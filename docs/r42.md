▎ I'm building a platform that hosts other people's self-hosted apps and wants a read-only "superadmin" view into each hosted app's own users/sessions/roles, by reading directly from the app's database (not through the app's own API). One of the apps I need to support uses Better Auth (the TypeScript auth library, better-auth.com). Give me the exact database schema Better Auth creates by default: table names, column names and types, for user, session, account, and any role/permission-related tables. Cover how this differs across its supported adapters (Drizzle, Prisma, Kysely, raw SQL) — is the actual table/column shape identical across adapters, or does it vary? Does Better Auth expose a documented, versioned schema contract I can rely on across upgrades, or is the schema considered an internal implementation detail that could change between minor versions? Include links to the official schema documentation and any migration/changelog history showing whether this schema has changed before.

Better Auth defines a versioned core schema comprising four primary tables (user, session, account, and verification) that maintain an identical logical shape across different ORM adapters and SQL dialects. While the core schema is treated as a stable, public contract committed to remaining consistent throughout the v1 lifecycle, table and column names can be customized or extended via plugins such as administration and multi-tenant organization modules. Das direkte Koppeln deiner Hosting-Plattform an die zugrundeliegende Datenbank einer gehosteten App (anstatt über eine API zu gehen) bringt erhebliche technische und architektonische Risiken mit sich.Nachfolgend findest du eine strukturierte, rein technische Risikobewertung für diesen Direct-Database-Access-Ansatz, bezogen auf moderne Authentifizierungs-Bibliotheken wie Better Auth, Lucia, Auth.js (NextAuth) und Ory Kratos. [1] (https://better-auth.com/docs/plugins/admin)1. Die technischen Risiken des direkten DatenbankzugriffsA. Cache-Invalidierung & State-Desynchronisation (Kritisch)Moderne Authentifizierungs-Frameworks verlassen sich zur Leistungsoptimierung stark auf Multi-Level-Caching. Wenn deine Plattform Daten direkt in die Datenbank schreibt, erfährt die Anwendung nichts von dieser Änderung.Better Auth: Unterstützt Mechanismen wie cookieCache (Speicherung verschlüsselter Session-Daten im Browser des Nutzers) sowie secondaryStorage (z. B. eine Redis-Schicht vor der Datenbank). [1] (https://better-auth.com/docs/concepts/session-management), [2] (https://better-auth.com/docs/guides/optimizing-for-performance)Das Problem bei Write-Zugriffen: Wenn du eine Session direkt in der SQL-Datenbank löschst oder den Status eines Nutzers auf banned setzt, bleibt die Session im Redis-Cache oder im verschlüsselten Browser-Cookie des Nutzers bis zum Ablauf des TTLs (Time-To-Live) aktiv. Der Nutzer behält vollen Zugriff, obwohl deine Hosting-Plattform ihn blockiert hat. [1] (https://github.com/better-auth/better-auth/discussions/9242), [2] (https://better-auth.com/docs/concepts/session-management)Das Problem bei Read-Zugriffen: Liest deine Plattform den Status "aktiv" aus der DB, kann dieser bereits veraltet sein, wenn die Anwendung eine Session im Cache, aber noch nicht in der DB als abgelaufen markiert hat (oder umgekehrt bei zustandslosen/stateless Übergängen). [1] (https://better-auth.com/docs/concepts/session-management)B. Schema-Drift und Plugin-VarianzSelbst wenn eine Bibliothek ein stabiles Kern-Schema garantiert, bricht der direkte Zugriff, sobald Plugins oder Anpassungen ins Spiel kommen.Erweiterungen durch die App: Better Auth erlaubt Entwicklern das dynamische Hinzufügen von Feldern über additionalFields oder Plugins (wie Multi-Tenant-Organisationen oder das Admin-Plugin). [1] (https://better-auth.com/docs/authentication/email-password), [2] (https://better-auth.com/docs/reference/options)Dynamische Spalten-Typen: Je nachdem, ob die App Drizzle, Prisma oder rohes SQL nutzt, können IDs als VARCHAR, TEXT oder native UUIDs angelegt sein. Ein starrer Lese-Mechanismus deiner Plattform wird bei abweichenden Datentypen oder benutzerdefinierten Tabellennamen (z. B. custom_user statt user) fehlschlagen. [1] (https://better-auth.com/docs/reference/options)Upgrades: Versionen innerhalb des v1-Lifecycles mögen abwärtskompatibel sein, aber Minor-Updates von internen Abhängigkeiten oder ORM-Adaptern können Indizes, Kaskadierungen oder Datums-Formate (z. B. ISO-Strings vs. Unix-Timestamps) verändern.C. Krypto- und Event-Bypass (Geschäftslogik-Verletzung)Ein Authentifizierungs-Framework tut beim Erstellen oder Ändern eines Datensatzes mehr als nur SQL auszuführen:Passworthashing: Wenn du einen Nutzer direkt in der Tabelle anlegst, umgehst du den dedizierten Krypto-Workflow der App (z. B. die korrekte Ableitung von Salt-Werten via Argon2id oder bcrypt).Lifecycle Hooks & Audits: Viele Enterprise-Setups triggern bei der Erstellung eines Nutzers Webhooks, erzeugen Audit-Logs oder senden Verifizierungs-Mails. Ein direkter DB-Insert hintergeht diese Logik vollständig – das System läuft asynchron. [1] (https://better-auth.com/docs/infrastructure/getting-started), [2] (https://itnext.io/why-you-shouldnt-implement-authorization-around-your-application-and-what-to-do-instead-35c7851bfd9f)2. Offizielle Admin- und Introspektions-APIs der BibliothekenDie Annahme, man müsse direkt auf die Datenbank zugreifen, um Daten zu verwalten, ist bei den meisten modernen Bibliotheken unbegründet. Sie bringen eigene, programmatische APIs mit, die genau für solche Server-zu-Server-Szenarien gedacht sind:BibliothekOffizielle Admin-/Management-API vorhanden?Funktionsweise für externe PlattformenBetter AuthJa (Über das Admin-Plugin)Bietet dedizierte Server-Endpunkte wie /admin/get-user, /admin/ban-user und /admin/list-user-sessions. Kann programmatisch über auth.api.getSession oder über sichere API-Key-Plugins von außen angesprochen werden.LuciaNein (Per Design)Lucia versteht sich als minimaler Session-Manager. Sie bietet bewusst keine integrierte Benutzerverwaltung (kein Registrierungs- oder Admin-UI). Hier steuert die App die DB-Logik selbst.Auth.js / NextAuthTeilweiseBietet Adapter-Methoden (z. Fazit und EmpfehlungFür reinen Read-only-Zugriff ("Superadmin"-Dashboard): Wenn du ausschließlich lesend zugreifst, ist das Risiko von Datenkorruption minimal. Do any existing hosting/PaaS platforms (Vercel, Render, Railway, Coolify, Supabase, Fly.io, or similar) offer a feature where the PLATFORM's own admin dashboard can see or manage the USERS and ROLES that a hosted application defines in its own auth system? I'm specifically interested in: (1) whether this pattern exists anywhere in production, (2) how it's implemented if so (documented API integration vs. reading the app's database directly), (3) what security/liability concerns are publicly discussed around a hosting platform having this kind of cross-boundary visibility into a customer's own app data, and (4) any post-mortems, security research, or forum discussions arguing this is a bad idea and why.

Hier ist eine detaillierte und rein technische Analyse dieses Architekturmusters im Kontext moderner Platform-as-a-Service (PaaS) und Backend-as-a-Service (BaaS) Anbieter.1. Existiert dieses Muster in der Praxis? (Production Footprint)Nein, bei reinen App-Hosting-Plattformen (PaaS) existiert dieses Feature nicht.Plattformen wie Vercel, Render, Railway oder Fly.io bieten keine plattformseitige Ansicht der Endnutzer oder Rollen einer gehosteten Anwendung. Sie agieren strikt auf Infrastrukturebene (Compute, Netzwerk, Storage) und betrachten den Speicherinhalt oder die Tabellen von Datenbanken als isolierte Blackbox des Kunden. [1] (https://vercel.com/i/railway-alternatives), [2] (https://render.com/articles/platforms-with-a-real-free-tier-for-developers-in-2026), [3] (https://www.reddit.com/r/webdev/comments/1l23vrt/simple_and_reliable_infra_for_my_web_app_render/)Ja, bei Backend-as-a-Service (BaaS) Plattformen existiert dieses Muster.Anbieter wie Supabase oder Firebase bieten genau dieses Feature an. Im Supabase-Dashboard gibt es einen dedizierten Reiter „Authentication > Users“, auf dem Plattform-Administratoren alle Endnutzer der gehosteten App einsehen, anlegen, sperren oder löschen können. [1] (https://supabase.com/docs/guides/auth/managing-user-data), [2] (https://www.youtube.com/watch?v=Q7P20fHJlm4)2. Wie wird es technisch implementiert?Es gibt in der Praxis zwei fundamentale Implementierungsansätze, wobei die Grenze zwischen API und DB-Zugriff fließend ist:Direktes Auslesen der Datenbank (Das BaaS-Modell):Supabase nutzt das Open-Source-Authentifizierungs-Tool GoTrue (geschrieben in Go). GoTrue läuft als separater Service neben der PostgreSQL-Datenbank. Das Supabase-Plattform-Dashboard liest die Nutzerdaten direkt aus dem geschützten auth-Schema der zugrundeliegenden Postgres-Datenbank (Tabelle auth.users). Da Supabase die Infrastruktur selbst verwaltet und das Schema kontrolliert, liest das Dashboard direkt die DB-Tabellen aus (bzw. nutzt die SQL-Konsole der Plattform im Hintergrund). [1] (https://supabase.com/docs/guides/auth/managing-user-data)Verwendung einer Control-Plane API (Das SaaS-Modell):Würde eine PaaS-Plattform dieses Feature für externe Auth-Bibliotheken (wie Auth0, Clerk oder ein selbstgehostetes Kratos/Better Auth) anbieten, erfolgt dies ausschließlich über dokumentierte Admin-REST-APIs. Die Plattform verlangt die Hinterlegung eines Master-API-Keys oder Admin-Tokens. Das Dashboard der Hosting-Plattform agiert dann als reiner API-Client, der standardisierte HTTP-Anfragen (z.B. an Ory Kratos' Admin-Port oder Better Auth's Admin-Plugin) schickt. Ein direktes Tunneln in die Anwendungsdatenbank wird hier vermieden.3. Sicherheits- und Haftungsrisiken (Security & Liability)Wenn eine Hosting-Plattform direkten Zugriff auf Endnutzerdaten erhält (insbesondere über den direkten DB-Weg), entstehen schwerwiegende rechtliche und architektonische Probleme, die in der Security-Community intensiv diskutiert werden:A. Datenschutz und rechtliche Haftung (GDPR / DSGVO / SOC2)Vom Daten-Transporteur zum Daten-Verarbeiter: Ein normaler Hoster (PaaS) ist oft nur ein Data Processor, der verschlüsselte Datenströme bereitstellt. Sobald die Plattform jedoch aktiv Endnutzerdaten liest, filtert und im eigenen Dashboard darstellt, wird sie tief in die Datenschutz-Compliance (GDPR) hineingezogen.Das Mandanten-Problem: Hat ein "Superadmin" der Hosting-Plattform Einblick in die E-Mail-Adressen, IP-Adressen oder Metadaten der App-Nutzer, reicht ein einziger kompromittierter Mitarbeiter-Account auf Plattformseite aus, um die Daten aller Kunden-Anwendungen offenzulegen (Cross-Tenant Data Leakage).B. Aufweichung des "Least Privilege"-Prinzips (Privilege Abuse)Um Passwörter zu validieren oder Sessions zu verwalten, benötigt die App Schreibrechte auf die Auth-Tabellen. Wenn deine Hosting-Plattform ebenfalls direkt in diese Tabellen schreibt, benötigt der DB-User der Plattform vollständige administrativen Rechte (DML/DDL) auf dem Kernstück der Anwendungssicherheit. Das widerspricht dem Prinzip der minimalen Rechtevergabe. [1] (https://baserow.io/blog/database-security), [2] (https://www.linkedin.com/pulse/top-10-database-security-risks-every-organization-must-asad-mahmood-84ntf), [3] (https://hostingb2b.com/blog/security/10-security-risks-and-solutions-for-your-databases/)C. Umgehung von Verschlüsselungsketten und App-LogikWenn die Plattform direkt in die DB schreibt, um beispielsweise eine Rolle zu ändern, erfährt die App-Logik nichts davon. Caches (Redis/In-Memory) werden nicht invalidiert, Event-Trigger (z.B. "Sende Willkommens-E-Mail bei neuem User") werden komplett umgangen.4. Post-Mortems und Core-Argumente gegen dieses MusterEs gibt in bekannten Sicherheitsforen (wie dem HN (Hacker News) oder r/selfhosted / r/cybersecurity) drei Hauptargumente und reale Vorfälle, warum eine solche tiefe Kopplung als schlechtes Design gilt:Das Supabase "Insecure Default" / security definer Sicherheitsrisiko (2022/2023)Der Kontext: Da das Supabase-Plattform-Dashboard eng mit der Postgres-Datenbank verzahnt ist, animierte es Entwickler dazu, Datenbank-Trigger zu schreiben. Wenn ein neuer Nutzer in auth.users (durch die Plattform oder API) angelegt wird, kopiert ein SQL-Trigger die Daten in eine öffentliche Profil-Tabelle (public.profiles).Das Problem: Viele Entwickler deklarierten diese Trigger fälschlicherweise als SECURITY DEFINER ohne expliziten search_path. Angreifer konnten dies ausnutzen, um über bösartige Payloads in den User-Metadaten Administratorrechte auf der gesamten Datenbank zu erlangen (Privilege Escalation via Postgres Triggers).Die Lehre: Die direkte Interaktion mit Auth-Tabellen auf Datenbankebene überfordert die meisten Anwendungsentwickler strukturell und führt zu kritischen Fehlkonfigurationen. [1] (https://pentera.io/glossary/database-vulnerabilities/), [2] (https://supabase.com/docs/guides/auth/managing-user-data), [3] (https://hostingb2b.com/blog/security/10-security-risks-and-solutions-for-your-databases/)Das "Blast Radius"-Argument (Plattform-Compromise)In Sicherheitsanalysen zu PaaS-Systemen wird oft das Szenario diskutiert, was passiert, wenn die Control-Plane der Hosting-Plattform (z.B. durch Social Engineering wie beim MGM Reseller Hack) kompromittiert wird.Wenn der Hoster nur Code ausführt, kann der Angreifer die App manipulieren. Wenn der Hoster aber direkten DB-Lesezugriff auf das Auth-Schema hat, kann der Angreifer sofort sämtliche passiven Nutzerdaten abgreifen (PII Leak), ohne erst Schadcode in die Container einschleusen zu müssen. Das erhöht den Blast Radius (Schadensradius) eines Plattform-Hacks dramatisch.Fazit für dein VorhabenWenn du eine Plattform baust, die andere Apps hostet, solltest du strikt davon absehen, die Datenbanken deiner Kunden nach Auth-Tabellen zu durchsuchen. Es ist architektonisch sauberer und sicherer, wenn du von den gehosteten Apps verlangst, einen standardisierten Webhook oder eine minimale Admin-API anzubieten, die dein Dashboard sicher abfragen kann.Falls du tiefer in die Materie einsteigen möchtest, lass es mich wissen:Sollen wir ein Konzept für eine sichere API-Schnittstelle (Sidecar-Muster) entwerfen, das deine Plattform nutzen kann, ohne die DB anzufassen?Möchtest du mehr darüber erfahren, wie Supabase das auth-Schema isoliert, um Angriffe auf Anwendungsebene zu blockieren?Vercel4 Railway alternatives for different application needs - Vercel08.09.2026 — Tools * Next.js. * Open Source. ... To mirror or reference external role data inside Open Policy Agent (OPA), you need to bridge a core architectural reality: OPA is designed for in-memory speed, meaning it prefers all authorization data to be locally available rather than pulling it synchronously over the network during a request evaluation.When dealing with a third-party application (where you do not own the database schema or the source of truth), your integration strategy depends on how frequently that external application alters its user permissions and how much access control you have over its infrastructure.Patterns for Synchronizing External Data into OPAThere are four primary architectural patterns for pulling external roles/users into OPA’s JSON data document structure.[ Third-Party App ] 
       │
       ├─── (Pattern 1: Push) ──────> [ Webhook Receiver ] ─── (Writes to) ───┐
       ├─── (Pattern 2: Pull) ──────> [ Platform Sync Worker ] ───────────────┼──> [ OPA Server / Sidecar ]
       │                                       │                              │     (Local JSON Data Memory)
       └─── (Pattern 3: Bundle) ───> [ Central Bundle Server ] ─ (Polls) ────┘
1. The Push / Webhook PatternThe third-party application or its underlying auth system emits an event payload (e.g., user.role.updated) whenever permissions change.How it works: Your platform hosts a microservice endpoint that acts as a webhook receiver. When an event lands, this service formats the payload into OPA-compatible JSON and uses OPA’s REST Data API (PUT /v1/data/external_roles) to mutate OPA’s in-memory storage.Trade-off: Minimal lag time, but it requires the hosted third-party application to support robust webhooks (like Clerk or Supabase do). If a webhook is missed due to a brief network blip, data drifts out of sync until a manual reconciliation runs.2. The Pull / Polling Worker PatternYour platform runs a background sync worker that routinely sweeps the third-party application's APIs or database schemas.How it works: A cron job or permanent loop calls endpoints like GET /admin/identities (Ory) or queries the database directly (SELECT * FROM auth.users). The worker calculates the diff or pulls a full snapshot, maps it into your desired Rego JSON schema shape, and issues a PUT request to update OPA's data state.Trade-off: Extremely resilient and simple to implement. However, it introduces data propagation latency (e.g., if you poll every 60 seconds, a user who was stripped of their Admin role in the third-party app might still have Admin privileges on your platform for up to a minute).3. The Central Bundle API ServerOPA has a built-in feature called the Bundle API. OPA can be configured to natively poll a remote HTTP server for tarball files containing raw Rego files (.rego) and static data documents (data.json).How it works: You build a specialized "Bundle Server." This server watches or queries your third-party apps, constantly builds optimized .tar.gz bundle files representing the state of the universe, and caches them. The OPA engines deployed across your platform check the Bundle Server periodically (e.g., every few seconds) using HTTP caching headers (ETag / If-None-Match) to efficiently download changes.Trade-off: This is the enterprise production standard for scaling OPA. It shifts the synchronization complexity away from your platform's core code and hands it over to OPA’s native, hardened networking loop.4. The Pull-on-Demand (Synchronous http.send) PatternInstead of storing user/role copies in OPA memory beforehand, OPA queries the third-party application live during policy evaluation.How it works: Inside your Rego policy, you use OPA’s built-in http.send() function to make an outbound REST call to the third-party application’s role endpoint, passing the user’s ID.Trade-off: Highly discouraged for low-latency paths. It completely breaks OPA's speed advantages, introduces a single point of failure (if the third-party app slows down, your authorization loop times out), and subjects the external application to aggressive rate-limiting or API exhaustion.Real-World Precedents: Third-Party EnforcementsUsing OPA to enforce policy based on a completely separate, third-party application's role definitions is a rapidly growing practice, driven by the emergence of Multi-Tenant SaaS Infrastructures, B2B Cloud Marketplaces, and Internal Developer Platforms (IDPs).Here are known real-world patterns and examples of this architecture:1. B2B Cloud Marketplace InteroperabilityWhen companies build extensions, add-ons, or plugins for large third-party ecosystems (like the Atlassian Marketplace or Salesforce AppExchange), the extension platform often does not manage user identities.The Architecture: The host application provides a signed JSON Web Token (JWT) containing custom claims about the user's role inside their company tenant.OPA Enforcement: The OPA policy is designed to parse the third-party JWT cryptographic signature, unpack the roles array out of the external claim namespace (e.g., claims.thirdparty_org_roles), and run Rego assertions directly against those external assignments without ever keeping a database copy of the user list.2. Cloud Custodian & Mesh Governance (External Directory Mapping)Enterprise governance platforms (such as Styra Declarative Authorization or multi-cloud asset orchestrators) frequently enforce strict operational boundaries across environments where the users are owned by client organizations using arbitrary external setups.The Architecture: Companies use a central OPA instance to lock down infrastructure or APIs, but map tenant mappings through a translation layer.OPA Enforcement: The JSON data document loaded into OPA behaves like an identity translation matrix:json{
  "tenant_mappings": {
    "external_app_alpha": {
      "roles": {
        "org_owner": ["platform_superuser", "billing_admin"],
        "content_editor": ["platform_viewer"]
      }
    }
  }
}
The Rego policy dynamically matches the incoming third-party role payload against this dictionary document to determine the local privileges allowed on your platform.
