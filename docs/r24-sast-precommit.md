Allerdings lässt sich das Prinzip von Pre-Commit-Hooks (Aktionen abfangen und validieren, bevor sie ausgeführt werden) mithilfe von eBPF (extended Berkeley Packet Filter) direkt im Linux-Kernel für System- und Dateizugriffe implementieren. LSM Hooks (BPF_PROG_TYPE_LSM)Das Linux Security Module (LSM) Framework bietet die mächtigste Möglichkeit für Pre-Commit-Entsprechungen im Kernel.Funktionsweise: LSM-Hooks greifen direkt vor der eigentlichen Kernel-Aktion (z. B. dem Schreiben einer Datei oder dem Starten eines Prozesses).Vorteil: Sie dürfen den Zugriff aktiv verweigern (indem sie einen Fehlercode wie -EPERM zurückgeben).Beispiel-Hooks: path_mkdir (bevor ein Ordner erstellt wird) oder file_open (bevor eine Datei geöffnet wird).2. fentry / fexit & kprobes (BPF_PROG_TYPE_TRACING)Funktionsweise: Diese Hooks klinken sich an den Anfang (fentry / kprobe) oder das Ende (fexit / kretprobe) beliebiger Kernel-Funktionen ein.Einschränkung: Reine Tracing-Kprobes können Daten meist nur beobachten, aber den Systemaufruf nicht direkt blockieren. Für ein "Pre-Hook"-Blocking-Szenario sind sie daher schlechter geeignet als LSM. Klassische Git-Hooks sind extrem unzuverlässig, weil sie lokal pro Repository eingerichtet werden müssen und von jedem Entwickler einfach mit --no-verify umgangen werden können. Auf Server-Ebene (z. B. pre-receive Hooks in GitHub/GitLab Enterprise) ist es oft zu spät oder erfordert teure Enterprise-Lizenzen.Die Idee, SAST (Static Application Security Testing), DAST (Dynamic Application Security Testing) und Secret-Scanning direkt in den Linux-Kernel via eBPF zu verlagern, um vor dem Commit alles abzufangen, stößt jedoch auf fundamentale architektonische Grenzen.Hier ist die ehrliche, technische Realität, warum das im Kernel extrem schwer ist – und wie du das Ziel trotzdem unumgehbar und zentral erreichst.Warum SAST/DAST und Secret-Scanning direkt im eBPF-Kernel-Hook scheiternDas Größen- und Komplexitätslimit von eBPF:Ein eBPF-Programm läuft in der Sandbox des Kernels und hat ein striktes Instruktionslimit (Komplexitätsgrenze). Ein SAST-Tool (wie Semgrep) oder ein Secret-Scanner (wie Gitleaks) muss komplexe Regex-Muster abgleichen, Entropien berechnen oder abstrakte Syntaxbäume (AST) analysieren. Das sprengt die Kapazität des Kernels bei Weitem.Kein Kontext zum "Commit"-Zeitpunkt:Wenn du im Terminal git commit tippst, weiß der Linux-Kernel nicht, dass gerade ein "Commit" stattfindet. Für den Kernel sind das nur hunderte isolierte Systemaufrufe (read, write, execve), bei denen Git die Dateien im .git-Ordner manipuliert. Der Kernel sieht den Code-Inhalt nur als rohe Byte-Ströme beim Schreiben auf die Festplatte.DAST benötigt eine laufende Anwendung:DAST testet eine ausgeführte Anwendung von außen (z. B. via HTTP-Requests). Zum Zeitpunkt eines Commits existiert die laufende Anwendung noch gar nicht.Die Lösung: Der "Hybrid-Ansatz" (eBPF fängt ab → Userspace scannt)Du kannst den Kernel zwar nicht den Scan machen lassen, aber du kannst eBPF als unumgehbaren Wächter (Gatekeeper) nutzen. eBPF blockiert die Git-Operation so lange, bis ein zentrales Tool im Userspace den Code gescannt und freigegeben hat.So sieht die Architektur für eine zentrale, unumgehbare Workstation-Sicherung aus:[Entwickler: git commit]
       │
       ▼
[Kernel: eBPF LSM Hook (file_open / bprm_check)] 
       │
       ▼  (Operation wird pausiert)
[eBPF Ring Buffer / Perf Event] ───> [Zentraler Daemon im Userspace]
                                            │
                                            ▼ (Führt Scans aus)
                                     [Gitleaks / Semgrep / Trufflehog]
                                            │
       ┌────────────────────────────────────┘
       ▼
[Ergebnis an eBPF zurück]
       │
       ├─► REFREIGEBEN (Code sauber)   ──► Commit wird ausgeführt.
       └─► BLOCKIEREN  (Secret/Vunl)   ──► Entwickler kriegt "Permission Denied".
Wie du das konkret umsetzt (ohne es für jedes Repo zu konfigurieren):Zentraler Security-Daemon auf den Entwickler-Maschinen:Du installierst ein Tool wie das Open-Source-Framework Tetragon von Cilium. Da Tetragon auf eBPF-LSM basiert, wird es einmalig systemweit als Systemd-Service gestartet. Es überwacht alle Repositories gleichzeitig.Überwachung des Git-Prozesses:Du konfigurierst den eBPF-Hook so, dass er anspringt, sobald der Prozess git versucht, die Datei .git/COMMIT_EDITMSG oder .git/index zu schreiben oder zu verändern.Der Scan-Trigger:In dem Moment, in dem eBPF den Schreibzugriff registriert, blockiert der Hook den Systemaufruf kurzzeitig und schickt die Dateipfade über einen eBPF Ring Buffer an deinen Userspace-Daemon. Dieser Daemon führt sofort gitleaks detect --source=/pfad/zum/repo aus.Enforcement:Gibt der Scanner 0 (sauber) zurück, erlaubt das eBPF-LSM-Programm den Schreibzugriff.Schlägt der Scanner an, gibt eBPF -EPERM (Operation nicht erlaubt) zurück. Der Commit schlägt fehl, egal was der Entwickler in Git konfiguriert hat.Gibt es das schon fertig?Es gibt keine fertige "Out-of-the-Box"-Software, die exakt "eBPF + Secret Scanning vor dem Commit" als ein fertiges Produkt verkauft, da dieser Ansatz extrem tief in das Betriebssystem der Entwickler eingreift (erfordert Root-Rechte auf den Laptops).In der Praxis lösen Unternehmen das Problem "Zentral & Unumgehbar" meistens über zwei pragmatischere Wege, die keine Konfiguration pro Repo erfordern:Variante A: Globale Git-Hooks via MDM (Mobile Device Management)Anstatt eBPF nutzt du die native Git-Funktion git config --global core.hooksPath /usr/local/bin/global-hooks. Diesen Befehl pushst du zentral über eure IT-Verwaltung (z.B. Jamf, Ansible, Intune) auf alle Laptops. In diesem globalen Ordner liegt ein einziges Skript, das vor jedem Commit Gitleaks/Trufflehog aufruft. Der Entwickler kann es nicht pro Repo deaktivieren.Variante B: Endpoint Detection & Response (EDR) mit eBPFModerne Sicherheits-Tools für Entwickler-Laptops nutzen eBPF (z. B. Es bringt einen eigenen, in Go geschriebenen Minikernel namens Sentry im Userspace mit. [1] (https://agent-sandbox.sigs.k8s.io/docs/use-cases/gvisor-isolation/), [2] (https://github.com/freedomofpress/dangerzone/issues/126), [3] (https://medium.com/@GiteshWadhwa/enhancing-container-security-with-gvisor-a-deeper-look-into-application-kernel-isolation-585af4652781), [4] (https://www.upwind.io/feed/unlock-runtime-visibility-for-gvisor-sandboxed-containers)Das Problem: Ein normales eBPF-Programm, das du auf dem Host (z.
